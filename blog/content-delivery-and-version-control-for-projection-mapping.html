Content delivery and version control for projection mapping

How to name, check, approve and transfer show files so the right version plays on show night, with a content delivery checklist for projection mapping.

BY FAHAD KHAN TAREENNOVEMBER 12, 20266 MIN READ
AKS FIELD NOTES← All articlesView projects ↗

Most last-minute problems at a projection mapping show are not technical failures. They are file problems: the wrong version on the playback machine, a render that nobody checked at full resolution, a revised logo that reached the designer but not the media server. When a show runs for a few minutes on a building at night, there is no room to discover that the file on the machine is not the one the client approved. This note describes how we handle content delivery at AKS, and what a client can do to make the process faster and safer.

Why file discipline matters more on large surfaces

A mapped show is a very large video, often rendered to a canvas much wider than a normal screen, and it can take hours to render and many more to copy, check and load. A single revision is expensive. If a change is discovered on site, the options are to re-render, re-transfer and re-test, or to live with the error. Neither is pleasant when a crew is waiting and an audience is expected.

The other reason is that many people touch the content: motion designers, sound designers, the client's brand team, the approving authority and the playback operator. Without a shared system, each of them holds a different idea of what "final" means. Good file discipline is simply a way of making sure everyone is talking about the same file.

Name and number every file the same way

We use one predictable naming pattern for everything that leaves the studio. It carries the project, the section, the version and the date, so anyone can tell what a file is without opening it. A name like project_scene03_v07_2026-11-12 is boring, and that is the point. Names such as "final", "final2" or "final_new" are traps, because none of them says which comes last.

  • Increase the version number with every change, including small ones. Never overwrite a file that has already been shared.
  • Keep the number of the approved version in the filename of the delivered show, so the approval can be traced.
  • Separate working files from delivery files. Project files, source footage and previews stay in one place; only checked renders go to the playback folder.
  • Write a short change note with each version: what moved, what was fixed and what was approved.

Approve against a preview, deliver a master

Clients should never be asked to approve a full-resolution file by email. Approval works better against a lightweight preview, usually a compressed video of the content on a model of the building. The preview is for judging story, timing and composition. It is not for judging sharpness or colour, which depend on the real surface and the real projectors.

Once a section is approved, we render the master separately and record which preview it came from. This keeps two questions apart: "did the client approve the design?" and "is the file technically correct?" Both need a clear yes before a section is locked. Our note on content review and approvals covers the approval side in more detail.

Check every master before it travels

A master render is checked before it is copied anywhere. We look at the following on every file, and we do it on the file itself, not on the preview:

  • Resolution and frame size. The pixel dimensions must match the canvas agreed for the show. A render that is slightly off can be scaled by the server, but it will look soft, and the cause may be hard to find under time pressure.
  • Frame rate. It must match the project frame rate. A mismatch causes judder or drift against the audio.
  • Duration. The file length must match the audio track and the cue list, to the frame.
  • Codec and container. It must be one the chosen media server plays smoothly. We discuss this in video codecs and frame rates for projection mapping.
  • Visual scan. Someone watches the full file once, start to finish, looking for dropped frames, black frames, compression blocks in dark gradients and any stray text or placeholder.

The visual scan is the step people skip, and it is the one that catches the most. A render can finish without an error message and still contain a corrupt stretch.

Copy with verification and keep two sets

Transferring content is a quiet source of failures. A copy that was interrupted can leave a file that looks complete but is damaged. Our practice is to copy, then compare checksums between the source and the destination so the files are known to be identical, rather than trusting the file size. Most operating systems include a tool for generating a checksum, and many file transfer tools can verify automatically.

We then keep at least two complete sets of the show. One is on the primary playback machine and one is on the backup, as described in our guide to backup and redundancy. A third copy stays off site or in cloud storage, so that a lost or failed drive does not mean a re-render. Each set carries the same version labels, so the operator can confirm in seconds that both machines hold the same show.

Freeze the content, and control changes after that

A content freeze is a date after which the show changes only for a defined reason. We agree it with the client early, and we set it well before show week. Before the freeze, creative changes are welcome. After it, changes are limited to fixes: a wrong name, a legal requirement, a technical fault.

Every change after the freeze goes through the same short routine. It is requested in writing, rendered as a new version, checked at full resolution, copied with verification to both machines and logged. This feels slow, but it is faster than the alternative, which is a verbal change on site that nobody records. If a client wants late creative changes, we plan for them by leaving a buffer in the show-week schedule.

What a client can do to help

Send logos and brand assets as vector files where possible, and send them once, with a note on which version is current. Name one person who can approve content and who will reply within an agreed time. Share the final wording, names and dates early, because text changes are the most common late request. And tell your studio about any approval that depends on a third party, such as a sponsor or an authority, so that time is reserved for it.

On projects from Parliament House in Islamabad to the Pakistan Monument, the content only reaches the surface cleanly because the files behind it are organised.
