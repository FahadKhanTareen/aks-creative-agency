Video codecs and frame rates for projection mapping

Which video codec and frame rate to render for projection mapping playback: intraframe versus long-GOP, file size, banding and a delivery checklist.

BY FAHAD KHAN TAREENOCTOBER 31, 20267 MIN READ
AKS FIELD NOTES← All articlesView projects ↗

Once a projection mapping animation is approved, someone has to turn it into a file that a media server can play without a single stutter on a very large canvas. The choice of video codec and frame rate is where many shows quietly go wrong. A file that looks perfect on a laptop can drop frames on a canvas several times wider than a monitor, and a frame rate that does not match the rest of the show produces a faint judder that audiences feel without being able to name. This note explains how we think about both choices, so that clients and content teams can agree on them before rendering starts.

Why playback is harder than it looks

A normal video player decodes one modest picture and sends it to one screen. A projection mapping server may decode a very wide image, cut it into regions, warp it to the building and send it to several projectors at once. All of that has to happen inside the time of a single frame, every frame, for the whole length of the show. The limiting factors are decoding speed, disk or storage throughput and the memory available to the graphics card. Our note on canvas resolution explains how large the canvas gets, and the codec decides how expensive that canvas is to play.

It also helps to separate two goals that are often confused. Delivery formats, such as the files used for streaming or sharing, are designed to be small. Playback formats for live shows are designed to be dependable and quick to decode, and they are usually much larger. We ask for the second kind, and we keep the small versions only for review.

Intraframe and long-GOP codecs

The most useful distinction is between codecs that store every frame on its own and codecs that store a frame by reference to its neighbours. Codecs in the H.264 and H.265 families usually work in groups of pictures, where most frames only describe changes from earlier or later frames. This makes small files, but jumping to an arbitrary point means the decoder must reconstruct several frames first. Under load, or when the server has to seek or loop, that extra work can show up as a stutter.

Intraframe codecs store each frame independently. Apple ProRes is a widely used example, and the HAP family and NotchLC are designed specifically for real-time playback in media servers and VJ software. Because every frame stands alone, seeking and looping are predictable. The price is file size, which can be many times larger than an H.264 file of the same picture. A show built around a single long file can therefore need a fast drive, and the production plan should state how much storage the server has.

HAP and similar formats lean on the graphics card for decoding rather than the processor, which leaves the processor free for warping and effects. Support varies between media servers, so the codec is one of the first things to confirm when choosing a media server. We do not assume that a format that works in one system is accepted by another.

Choosing a frame rate

The frame rate of the content should be decided once, early, and held for the whole show. Common choices are 24, 25, 30, 50 and 60 frames per second. Slower rates look more filmic and need less data, while higher rates make fast motion smoother, which matters on large surfaces where a sweep across a façade covers a lot of physical distance in a single second.

What matters more than the number is consistency with everything else the server drives. Projectors, LED processors and any audio or lighting timecode all run at their own rates. If the content is rendered at a rate that does not divide cleanly into the output refresh rate, some frames are shown for longer than others, and smooth movement picks up a rhythmic hitch. We confirm the output rate of the projectors and the timecode rate of the show control system first, and then pick the content rate that fits both. The timecode note covers the show control side.

The file itself should have a constant frame rate. Files recorded from phones, screen captures and some editing exports can have a variable frame rate, which causes drift against sound and against other layers. If a clip arrives that way, it should be converted before it goes anywhere near the show.

Colour, bit depth and banding

Large, smooth gradients are common in projection content: a glow across a dome, a slow fade in a night sky. Eight-bit video can show visible steps in those gradients, and a bright projection on a big surface makes the steps easier to see than they would be on a monitor. Higher bit-depth codecs reduce the problem, and a small amount of fine noise or grain added in the render also breaks up banding. We check gradients on a real projection before approving a file, because a laptop screen hides the issue.

Colour space should be stated as well. Content graded for a standard video colour space can look different once it passes through the server and the projector. The practical answer is to agree one working space with the server operator and test a reference pattern, as we describe in our note on colour and contrast.

Alpha, layers and splitting the canvas

Some scenes need transparency, for example a glow that sits over a live layer or a title that is composited by the server. Only some codecs carry an alpha channel, and that capability must be asked for at the start. Rendering a flattened picture is safer for pure playback, and layering in the server should be kept for elements that genuinely have to react to cues.

Very wide canvases may exceed the size limit of a single file in a given codec. In that case the picture is split into parts, one for each output or each region, and the parts must stay perfectly in step. We name the parts clearly, render them with the same settings from the same project and test them playing together, rather than assuming that identical settings give identical timing. The overlap between parts is described in our note on edge blending.

Test before you commit

The only reliable way to choose is to test. We render a short, demanding section of the real content, such as the busiest scene, and play it on the actual server at the full canvas size. We run it looped for a long period and watch for dropped frames and for any heat or storage problems. Then we run the same clip alongside the audio, so that sync drift would be obvious. A fast and thorough test early is far cheaper than discovering a problem during show week, when the content team has gone home.

It is also good practice to keep the master files in a high-quality format and generate playback files from them, so the show can be re-rendered in another codec if the server changes. Our backup note explains why every playback file should also exist on a second drive.

A codec and frame rate checklist

  • The media server operator has confirmed which codecs and maximum file sizes it plays.
  • One frame rate is chosen for the whole show and matches the output and timecode rates.
  • Every file has a constant frame rate, with no variable-rate clips.
  • Playback files use an intraframe or real-time codec, and review copies are kept separate.
  • Gradients have been checked on a real projection for banding.
  • The colour space and any alpha requirement are written down before rendering.
  • Split canvas parts share settings and have been tested playing together.
  • The busiest scene has been looped on the real server at full canvas size.
  • Master files are archived, and playback files are copied to a second drive.

Getting these decisions right is mostly about making them early and writing them down.
